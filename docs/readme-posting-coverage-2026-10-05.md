# 전체 공고 보존과 준비 단계 검수

2026-10-05. API-04 / WEB-08. 배포 여부는 게시판 OPS-01의 실제 릴리스 기록으로 확인한다.

## 수정 이유

기존 준비 단계는 요건을 최대 8개만 추출하면서 의미 검수에는 명시 요건 누락을 금지했다. 사용자가 제공한 FE 인턴 공고를 운영 릴리스로 별도 재현했을 때, 인용 8개가 모두 정확했지만 우대사항 등의 누락 때문에 `profile_semantic_review_failed`가 발생했다. 원래 사용자 호출의 모델 응답은 보관하지 않으므로 이 재현과 원래 호출의 내부 사유는 구분한다.

## 변경

- 전체 업무·필수·우대 요건을 보존하며 총 64개를 자원 상한으로 둔다. 상한에 맞추기 위한 선별이나 조용한 잘라내기는 허용하지 않는다. 원문 인용과 전체 범위·의미 검수는 유지한다.
- 인턴의 보조·일부 업무, 필수/우대, 기술 예시·선택지를 유지한다. 고용조건·지원방법·제출서류·업무 범위 한정 문구는 기존 `other` 종류에 원문 인용으로 보존한다. 회사 홍보·복지·일반 전형 순서는 원문에 남으며 지원자 평가 요건으로 만들지 않는다.
- 독해 조건은 평가 요건 8개씩, 최대 두 Codex 호출을 병렬로 처리한다. 각 배치는 공고 전체를 보고 정확히 배정된 요건에만 조건을 반환한다. 첫 실패를 보존하고 나머지 호출의 취소·정리를 기다린다. 기존 준비 제한 180초를 공유한다.
- Jev의 질문 후보는 내부 정책상 요청당 32개씩 모두 검사한다. 모든 청크가 검증된 뒤 질문을 선택한다. 뒤 청크 실패 시 의미 상태를 되돌리고 실제 호출·토큰 사용량은 유지한다.
- 고용·제출 안내로 역량 부족을 추정하거나, 이력서 한 파일만 보고 포트폴리오 미제출을 단정하지 않도록 작성·검수 경계를 공유한다.
- 운영 진단에는 단계·고정 실패 코드·경과시간만 남긴다. 모델의 검수 설명, 예외 상세, 이력서 원문은 기록하지 않는다. 화면은 일반 검증 실패를 인용 불일치로 단정하지 않고, 이전의 8개 제한과 공고를 줄이라는 안내를 제거한다.

## 측정 및 한계

동일한 공고만 사용한 수정 후 재현: 준비 133.078초, 업무 5개·필수 4개·우대 8개와 참고사항 6개, 총 23개 원문 인용이 정확하며 최종 범위 검수를 통과했다. 독해 기준은 평가 항목 17개에 각각 연결됐다. 아티팩트는 보호된 `.local/readme-lab-production/tilda-coverage-v1/`에 있다. 원래 실패 재현은 `tilda-diagnosis/`에 보존한다.

64개 보존은 최대 길이 문서와 64개 기준의 완주 보장이 아니다. 600회 호출·2,000,000 입력 토큰·읽기 제한 시간은 유지하며 초과하면 실패와 부분 결과를 전달한다. Jev 순차 판단은 여전히 본인 역할과 비교 성과 근거 중심이다. `method`만 있는 기준은 Jev가 순차 평가하지 않으며 전체 원문과 요건을 보는 최종 리포트 범위와 구분한다. 사람이 검토한 일반 판단 정확도나 실제 채용 결과를 의미하지 않는다.

자동 회귀는 64개 마지막 요건·인용, 누락 검수 유지, 두 배치 동시성, 실패 후 잔존 호출, 40번째 후보 선택, 뒤 청크의 잘못된 응답·예산 소진과 상태 복구, 진단 로그 비밀정보 배제를 확인한다. 프런트 독립 DOM 검증은 64개 혼합·64개 평가·참고사항만·빈 배열의 확인/독해/리포트 화면을 검증했다. 실제 모델 독해·리포트, CI 및 공개 브라우저 증거는 완료 후 별도 게시한다.
