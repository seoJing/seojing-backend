# README Laya·Codex 판단 품질 연구와 실행안

2026-10-04 KST. 조사와 합성 진단을 완료한 문서다. 아래 개선 구조·목표치는 **제안**이며, 모델 본학습·품질 승인·배포 완료를 뜻하지 않는다. 현재 API는 [readme-lab.md](readme-lab.md), 상태 확장 제안은 [readme-reader-v2.md](readme-reader-v2.md)를 따른다. 이번 작업은 진단 도구·합성 사례·이 문서만 추가했고 서비스의 프롬프트, 가중치, 화면 계약을 바꾸지 않았다.

## 판단

사용자가 정한 **공고 → 독해 기준 → Laya의 순차 독해 → Codex 리포트** 흐름은 유지할 가치가 있다. 다만 현재 구현은 공고별 기준을 실행 가능한 확인 조건으로 만들지 않고, Laya에는 추상적인 분류와 짧은 주변 문장만 주며, Codex에는 화면에 나온 메모의 근거만 준다. 학습량을 늘리기 전에 **무엇을 판단하는지, 필요한 근거를 받았는지, 언제 판단을 보류하는지**부터 고쳐야 한다.

추천 역할은 다음과 같다. 사람처럼 읽는 화면 연출은 이 상태 기록을 표현한다. 자유롭게 생성한 속마음을 판단 근거로 사용하지 않는다.

| 담당                 | 책임                                                                                | 품질을 확인할 단위                         |
| -------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------ |
| Codex CLI: 공고 준비 | 공고의 명시 요건과 그것을 확인하는 독해 질문을 구분하고, 근거·반례·충족 조건을 작성 | 공고 인용과 기준의 의미 일치               |
| Laya: 순차 판단      | 현재 문장과 읽은 범위에서 주체·행동·관련성·질문과의 관계·근거 후보를 선택           | 작고 명확한 선택 문제, 문서 전체 상태 변화 |
| 서버: 기억과 정책    | 원문·인용·경험 범위·질문 이력을 보존하고 전이 조건을 적용                           | 미래 정보 차단, 중복 방지, 상태 일관성     |
| Codex CLI: 리포트    | 확정된 기록을 설명하고 구체적인 수정 방향을 제시                                    | 문장별 근거 충실성, 유용성, 중복 여부      |

여기서 해소는 “그 질문에 필요한 설명이 문서에 있다”는 뜻이다. 경험의 진위·실제 역량·채용 가능성을 인증하는 뜻이 아니다.

## 1. 현재 구현에서 확인한 병목

| 관찰한 구현                                                             | 품질에 미치는 영향                                               | 먼저 바꿀 방향                                   |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| `python/runtime.py`의 고정 signal/missing/relation/relevance 질문       | 직무 기준과 연결된 독해보다 일반 문장 분류에 가까움              | 공고 기준과 facet의 확인 조건을 실제 입력에 포함 |

| 보정되지 않은 공통 confidence 0.65                                      | 높은 점수가 의미적 정답을 보장하지 않음                          | 분류별 보정과 오류·판단 범위의 동시 평가         |
| `codex.ts` report 입력은 notes의 evidence ID에 든 문장·연결 요건만 포함 | Laya가 메모/근거 연결을 놓치면 Codex가 복구할 정보 자체가 없음   | 화면 메모와 내부 근거 수집을 분리                |
| 보고서 검증은 ID·범주·연결 관계 중심                                    | 인용 ID가 맞아도 문장이 근거를 과장할 수 있음                    | 주체·시제·범위·수치·인과를 보는 의미 검증        |

실제 합성 40문장 실행 기록에서는 메모 1개·리포트 1개만 남았다. 이후 문장들은 Codex 입력에서 빠진다. 다만 각 문장이 서로 다른 회차 경험일 수 있으므로 “나중 문장이 첫 질문을 모두 해결한다”고 해석하지 않는다. 확인한 것은 **근거 전달의 병목**이다. 이전 40개 반복 메모를 1개로 줄인 것은 화면 잡음 감소이지 독해 정확도 향상 증거가 아니다. 로컬 증거: `.local/readme-laya/e2e-long.json`.

## 2. 이번에 직접 실행한 진단

### Laya: 기본 모델과 질문 표현

합성 32사례를 작성했다. unit 8개는 signal과 missing 두 판단을 하므로 변형당 40개 판단이다. 관계 12개, 공고 관련성 12개도 포함한다. 라벨은 실행 전에 작성한 **에이전트의 임시 기준**이며 사람 검수 전이다. 애매한 5사례는 복수 라벨을 허용한다. 이 데이터는 이미 관찰한 개발용 진단으로, 이후 비공개 최종 평가셋으로 재사용하지 않는다.

동일한 한국어 입력·기본 체크포인트·`lang="ko"`에서 질문 언어와 선택지 순서만 비교했다. 최종 실행은 5변형, 총 200개 head 판단이다.

| 변형                    | 임시 라벨 일치 | confidence ≥ 0.65인 판단 | 그중 임시 라벨 불일치 |
| ----------------------- | -------------: | -----------------------: | --------------------: |
| 현재 한국어 질문        |          14/40 |                       18 |                    12 |
| 현재 한국어 그대로 반복 |          14/40 |                       18 |                    12 |
| 한국어 선택지 역순      |          13/40 |                       18 |                    10 |
| 영어 질문·선택지 설명   |          10/40 |                       20 |                    15 |
| 영어 선택지 역순        |          10/40 |                       13 |                     9 |

한국어 동일 조건 반복에서 선택 라벨 변경은 0/40이었다. 선택지 순서를 뒤집으면 한국어 14/40, 영어 12/40이 바뀌었다. 한 번의 반복 대조이므로 모든 실행의 결정성을 보장하지는 않는다. 영어 번역이 한국어 이력서 판단에 도움이 된다는 가설은 이번 사례에서 지지되지 않았다.

예를 들어 “저는 SQL로 주간 판매 보고서를 작성했습니다”의 구체성을 claim으로 선택한 점수는 약 0.877이었다. 역할이 이전 문장에 있는데 다시 role을 고른 사례도 있었다. 임계값 조정만으로 의미 판단을 해결했다고 볼 수 없다.

해석 경계:

- 수치는 제품 정확도가 아니라 임시 라벨과의 일치다. 보수적인 `unrelated`와 `uncertain` 차이도 불일치에 포함될 수 있다.
- relation/relevance를 서비스의 concrete 조건과 무관하게 직접 호출했다. 0.65 이상 집계에는 none/uncertain도 포함된다. 화면 메모 생성률·잘못된 해소율이 아니다.
- state 토큰 잘림과 선택지 토큰열의 완전 중복은 거부했다. 선택지 설명 일부나 지시문의 잘림까지 검증하지 않았다. upstream은 선택지 설명을 최대 48토큰으로 자를 수 있어 추가 점검이 필요하다.
- 실행 순서가 고정돼 있고 unit 호출 시간은 두 head에 중복 기록된다. 이 자료로 변형별 속도를 비교하거나 기록 시간을 합산하지 않는다.

사용 환경: Mac mini arm64, MPS eager, 4 threads, `max_len=1024`, `head_max_len=256`; Laya 0.3.25, SDK SHA `8a976468b57c1b53541363dc86523263c9b68d34`; `convaiinnovations/laya-multilingual` revision `e4e9ddf21a7b1903b7acffd8814ad4307bf63a67`, weights SHA256 `9d628fd971b700382ac6f65920a86f149777b2e748e0c955fb3b19695aa8f204`.

증거: `test/fixtures/readme/quality-diagnostic.json`, `src/services/readme-lab/python/quality_probe.py`, `.local/readme-laya/quality-probe-20261004-final.json` 및 같은 이름의 `.log`. 최종 JSON에 dataset/probe/runtime SHA와 모든 선택·확률을 기록했다. 앞선 3변형 실행 파일은 보존했고, fixture 포맷 정리 후 최종 실행을 별도 파일로 생성했다.

### Codex: 현재 프롬프트의 경계 점검

실제 `/opt/homebrew/bin/codex`와 현재 서비스 프롬프트로 공고 3개·리포트 2개를 실행했다. reasoning effort는 현재값 low, 요청 모델은 cli_default다. 실행 결과에 실제 해석된 모델 ID가 없으므로 특정 모델의 재현 가능한 벤치마크라고 부르지 않는다.

| 합성 사례                                  | 직접 읽어 확인한 출력                                 | 남은 평가 과제                                                      |
| ------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------- |
| 담당업무 + 경력 무관 + 식사/교육비         | 일정 조정·안내문 작성 추출, 복지 제외, 경력 무관 유지 | `other`인 경력 무관을 이후 가점/감점 조건으로 쓰지 않도록 정책 필요 |
| Java 필수 + 성능 개선 우대 + 자격증 비필수 | 필수·우대 구분, 자격증 필수화 없음                    | 복잡한 예외·부정·우회 표현 추가                                     |
| 자세한 업무 추후 안내                      | 요건 빈 배열과 경고                                   | 없는 기준을 채우지 않는 상태 유지                                   |
| k6 가상 사용자 500명, 실제 고객 운영 아님  | 가상/실제 구분과 제한 보존                            | 검토 안내보다 구체적인 수정 조언 필요                               |
| 팀 보고서, 개인 역할 질문만 존재           | 질문을 역량 사실로 바꾸지 않음                        | “원문 검토 필요” 대신 무엇을 추가할지 설명 필요                     |

5사례에서 의도한 경계 위반은 관찰하지 못했다. 독립 사람 평가·다회 반복·다른 프롬프트 비교를 하지 않았으므로 100% 정확도라고 보고하지 않는다. 현재 “메모만 묶고 새 판단을 하지 말라”는 지시가 반복·소극적 문구에 기여했을 가능성이 있다. 이는 후속 비교 실험에서 검증할 가설이다.

## 3. Jev·Laya 사례에서 가져올 것

**Jev 자체와 Laya로 Jev를 대체한 사례는 구분한다.** Jev upstream은 TypeSafe 판단 모델이 관찰한 후보 중 행동·대상을 고르고, 필요한 텍스트만 별도 모델이 생성하는 구조다. 실행기는 대상의 유효성을 다시 검사하며 DONE도 독립 결과 확인이 필요하다. 우리에게 적용할 점은 “실제 존재하는 근거 후보 중 선택”과 “모델의 완료 선언을 서버 검증 없이 확정하지 않기”다. [Jev 소스, SHA 고정](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/README.md).

**Laya의 초기 브라우저 예제는 입력 설계의 중요성을 보여준다.** 전체 후보표를 state JSON에 넣으면 토큰 제한으로 정답 후보가 사라졌다. 후보 설명을 선택지 쪽으로 옮긴 같은 데이터 실험에서 live suite가 6/16에서 10/16으로 바뀌었다고 저자가 보고한다. 실제 목표 대상을 먼저 고른 뒤 요청 문장을 생성하고, 끝난 상태와 아직 끝나지 않은 상태를 함께 학습했다. 낮은 confidence를 큰 로컬 모델에 넘기는 방식은 그 실험에서는 악화됐다. 이 결과는 브라우저 과제의 프로젝트 보고이며 한국어 이력서 성능을 입증하지 않는다. [v10 계열 학습 사례](https://nandhakishorm.github.io/laya/finetune_browser_agent/).

**최신 사례의 실패까지 봐야 한다.** 2026-09-29 v19s 카드에는 Suite B 54/54와 더 어려운 미학습 사이트의 다단계 Suite C 11–14/54가 함께 있다. 실사이트 실패 중 약 60%가 조기 DONE이며 여러 학습·계획 변형으로도 해결되지 않았다고 한다. v19의 개선에는 실행 환경 수정도 포함된다. 우리의 “관련 설명을 찾았으니 질문이 다 풀렸다”는 오판과 비슷한 위험으로 참고하되, 이는 과제 간 유추다. 브라우저 가중치를 이력서에 그대로 쓰지는 않는다. [v19s 모델 카드, revision 고정](https://huggingface.co/cklxx/laya-browser/blob/645cf366a2ae35f1086e8c20eff48f909bb49206/README.md).

**스페인어 전화 분류 예제는 학습 방법을 참고한다.** 저자 작성 217사례에서 기본 모델 0.396 → 파인튜닝 0.912를 보고하지만 독립 평가셋은 아니다. 영어 선택지가 유리했던 현상은 이번 한국어 진단에서 재현되지 않았다. 가져올 것은 정답 유형을 먼저 정한 문장 생성, 긍정·부정 양방향 반례, 선택지 순서/도메인 변화, 평가 중복 제거다. 같은 예제에서 높은 confidence만으로 오류가 없어지지 않았고 INT8이 선택 결과를 바꿨으므로, 보정과 압축은 별도 검증한다. [동일 SDK의 전화 분류 연구](https://github.com/NandhaKishorM/laya/blob/8a976468b57c1b53541363dc86523263c9b68d34/research/benchmarks/es_phone_turns/README.md).

## 4. Laya가 풀 문제를 더 작고 명확하게 만들기

예를 들어 공고에 “운영 서비스의 성능 개선 경험 우대”가 있고 이력서에 “응답 시간을 30% 줄였다”고 쓰였다면, 곧바로 역량 점수를 내지 않는다. 같은 경험에서 본인의 행동, 전후 측정 기준, 실제 운영/실험 여부 중 **이 주장에 필요한 설명**을 확인한다. 모든 경험에 숫자나 특정 도구를 요구하는 새 채용 기준을 만들지 않는다.

후보 판단을 다음처럼 분해해 비교한다. 최종 head 수는 평가로 정하며 모든 문장에 모두 실행하지 않는다.

| 판단          | 가능한 선택의 예                               | 막으려는 오류                     |
| ------------- | ---------------------------------------------- | --------------------------------- |
| 관련 기준     | 제공한 criterion 후보 / none                   | 관련 없는 직무 조건에 연결        |
| 주체          | 본인 / 팀 / 타인 / 불명확                      | 팀 성과를 개인 역할로 확정        |
| 서술 상태     | 수행 / 계획 / 부정·정정 / 불명확               | 앞으로 할 일을 과거 경험으로 확정 |
| 확인 항목     | 역할 / 방법 / 결과 / 비교 근거 / none          | 이미 설명한 내용 반복 질문        |
| 질문과의 관계 | 충분한 설명 / 일부 설명 / 무관 / 충돌 / 불명확 | 키워드가 나왔다는 이유로 해소     |
| 근거          | 읽은 범위의 실제 span 후보 / none              | 없는 인용이나 다른 경험 인용      |

원문 인용 장부와 해석 장부를 분리한다. 원문은 불변이며, 해석에는 criterion, facet, 근거, 현재 위치, 상태·정책 버전을 붙인다. 나중에 틀렸다고 판단해도 최초 질문을 지우지 않고 정정 전이를 남긴다. 같은 경험인지 확실하지 않으면 연결을 보류한다.

입력은 현재 문장, 필요한 과거 인용, 기준의 충족/반례 조건, 비교할 질문으로 제한한다. 전체 공고·전체 이력서를 반복 투입하지 않는다. 후보를 줄인다면 정답 후보가 후보군에 들어오는 비율도 측정해야 한다. 모델이 잘 골라도 후보 생성에서 빠지면 전체 시스템은 실패다. 질문을 순환 검사하고 문단 경계에서 누락을 점검하는 방식도 비교한다.

토큰 예산은 문자열 길이가 아닌 실제 tokenizer 결과로 검사한다. 긴 선택지에 중요한 구별 조건을 끝에 몰아넣지 않는다. `options_distinct`만으로 설명이 온전히 보였다고 판단하지 않는다. 현재 32사례의 실패가 잘림 때문이라고 확인한 것은 아니며, 입력 형식을 바꿀 때 예방적으로 측정할 항목이다.

처음에는 전문가가 작성한 올바른 과거 기억을 넣은 경우와 실제 모델이 만든 기억을 넣은 경우를 비교한다. 전자도 틀리면 선택 문제/모델/라벨의 문제, 후자만 틀리면 누적 기억·후보 선택의 문제가 크다. 이 분리 없이 파인튜닝하면 데이터로 시스템 버그를 덮게 된다.

공고가 바뀔 때는 인용된 요건과 확인 조건을 입력으로 교체한다. 공통 모델은 여러 공고에서 주체·근거·질문 관계를 읽는 능력을 학습한다. 처음 보는 공고에도 이 능력이 유지되는지 따로 평가한다.

오프라인에서는 Codex CLI에도 **같은 prefix·같은 후보·같은 출력 문제**를 주어 기준선을 만든다. Codex도 자주 틀리면 라벨 정책과 입력의 충분성부터 확인하고, Codex는 맞히지만 Laya가 틀리면 학습·표현력 쪽을 집중 점검한다. 이것은 아직 실행하지 않은 비교이며, 실행 중 독해를 Codex로 대체하는 계약 변경과는 별개다. teacher로 쓸 Codex도 이 기준선을 통과해야 한다.

## 5. Codex의 역할도 평가 가능한 두 작업으로 나누기

**공고 준비:** 먼저 명시된 업무·필수·우대·예외를 인용과 함께 추출한다. 이후 각 요건을 읽기 위한 확인 조건을 작성한다. 원문 요건과 일반적인 글 설명력 점검을 서로 다른 출처로 표시한다. 이력서를 보기 전에 기준 버전을 고정한다. quote substring 검증뿐 아니라 “이 인용이 정말 지원자 요건인가, 부정을 뒤집지 않았는가”를 따로 평가한다.

**리포트:** 화면 메모 목록은 충분한 입력이 아니다. 내부 장부의 채택·보류 근거, 질문 상태 변화, 해당 원문과 필요한 인접 문장, 관련 공고 조건을 함께 제공한다. 모델이 놓쳤거나 맥락이 잘린 영역은 “설명이 없다”로 바꾸지 않는다. 전체 독해 뒤 추가 점검에서 근거를 새로 찾는 기능을 도입한다면 최종 점검 출처로 기록하고 과거 독해 시점에 소급하지 않는다. 이 경로는 현재 계약에 없다.

리포트 항목은 **무엇이 적혀 있는지 → 어떤 설명이 남았는지 → 무엇을 보완하면 좋은지 → 연결 인용**으로 구성한다. 예를 들어 “팀이 보고서를 작성했다고 적혀 있습니다. 본인이 담당한 구간이 드러나지 않습니다. 직접 작성한 항목과 사용한 자료를 한 문장 덧붙이면 역할을 판단하기 쉽습니다.”처럼 쓴다. 제공하지 않은 담당 구간을 대신 만들어 주지 않는다.

초안 생성 후 각 결론을 근거와 대조한다. ID가 존재하는지는 코드가 검사하고, 인용이 결론을 실제로 뒷받침하는지는 별도 판단 문제로 평가한다. 주체 변경, 계획→수행, 가상→실제 사용자, 상관→인과, 문서 미기재→능력 없음이 대표 반례다. [AlignScore의 근거-주장 정합성 접근](https://aclanthology.org/2023.acl-long.634/)은 평가 개념으로 참고하며, 해당 모델을 한국어 이력서 검증기로 바로 적용하지 않는다.

같은 모델에 “다시 잘 생각해”라고 요청하는 것만으로 검증이 되지는 않는다. 검사 항목·원문·오류 유형을 제공하고, 재검토가 실제 오류를 줄이는지 사람 평가와 비교한다. [자기 수정 연구 조사](https://aclanthology.org/2024.tacl-1.78/)는 신뢰할 수 있는 외부 피드백의 중요성을 지적한다. 2024년 결과를 모든 현재 모델의 한계로 일반화하지 않는다.

Codex는 기존 ChatGPT 로그인 CLI를 계속 사용한다. 가능한 실행 모델을 고정하고 CLI 버전·프롬프트·스키마·설정 해시를 기록한다. 동일 사례에서 low/medium/high를 비교해 실제 이득이 있는 단계에만 추가 추론 시간을 쓴다. 이는 모델 API 도입이나 완전한 로컬 추론 전환이 아니다. 작업별 평가·실패 분류·사람 판단과 평가기의 일치를 강조하는 [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 로컬 평가 방식에 적용한다.

**선택적 확장안:** 어려운 충돌·해소 후보만 문단 경계에서 Codex에 재검토시키는 방식도 비교할 수 있다. 기본안은 Laya 순차 판단을 유지하고 Codex를 오프라인 라벨 초안·공고·리포트에 쓰는 것이다. 실행 중 Codex 판정 추가는 현재 역할/계약의 확장이므로 별도 설계가 필요하다. 시험한다면 같은 prefix, 호출 상한, 타임아웃, 미응답 시 보류, 판단 출처를 갖추고 품질·지연을 같이 측정한다. 큰 모델이라는 이유만으로 정답 취급하지 않는다.

## 6. 학습 전에 정답과 평가를 만든다

1. **라벨 정책과 기준 사례:** 역할·방법·근거별 충분/부분/무관/충돌의 경계를 정한다. 약 30개 사례를 사람이 검토해 모호한 정의를 먼저 수정한다. 인사담당자의 숨은 판단이 아니라 문서에 있는 설명과 질문의 관계를 라벨링한다.
2. **작은 개발 데이터:** 예컨대 개발·운영·사무 3범주의 60개 기본 경험 × 6개 읽기 시점, 약 360상태로 입력/라벨 체계를 시험한다. 초기 비용 산정용 제안이며 충분한 학습량이라는 주장이나 성능 보장은 아니다.
3. **알려진 사실에서 생성:** 주체·행동·시점·측정값·정답 근거를 먼저 정하고 자연어를 생성한다. 생성문이 조건을 바꾸거나 답이 둘 이상 가능하면 제거/재검토한다. Codex 초안에 사람 승인 표시를 자동으로 붙이지 않는다.
4. **그룹 단위 분리:** 기본 경험·공고·문장 템플릿 계열을 train/dev/calibration/test 사이에 나눈다. 같은 이야기의 바꿔쓰기와 prefix들이 양쪽에 들어가지 않게 한다. 최종 평가 라벨은 튜닝에서 보지 않는다.
5. **실제 순차 실패 수집:** 모델을 끝까지 실행해 잘못된 질문과 기억이 생긴 상태도 정답을 붙인다. 늘 올바른 과거 상태만 주고 학습하지 않는다. DAgger의 모델이 방문한 상태에서 교정한다는 원칙을 적용한 제안이다. 원문 읽기 순서는 고정이고, 예측에 따라 달라지는 것은 기억/질문 상태다. [DAgger 원 논문](https://proceedings.mlr.press/v15/ross11a.html).

행동별 반례는 정답률 한 숫자보다 중요하다. 아래는 [CheckList의 행동 테스트](https://aclanthology.org/2020.acl-main.442/)를 우리 과제에 적용한 테스트안이다.

| 바꾸는 것                                    | 기대 변화/불변성                                 |
| -------------------------------------------- | ------------------------------------------------ |
| “제가 작성” ↔ “팀이 작성”                    | 본인 역할 확인 여부는 바뀌어야 함                |
| “개선했다” ↔ “개선할 계획”                   | 수행 근거 여부는 바뀌어야 함                     |
| “운영했다” ↔ “운영하지 않았다”               | 부정을 무시하면 실패                             |
| 동일 프로젝트 ↔ 별도 프로젝트의 같은 수치    | 질문을 해소하는 경험 연결이 달라져야 함          |
| 답을 뒤에 추가                               | 추가 전에는 미해소, 해당 문장을 읽은 뒤에만 해소 |
| 아직 읽지 않은 뒤 문장 교체                  | 이전 시점의 판단은 동일해야 함                   |
| 프로젝트 이름·비본질적 서식·선택지 순서 변경 | 의미가 같으면 판단 유지                          |
| 역할이 먼저 등장, 세 문단 뒤 성과 등장       | 이미 설명한 역할을 다시 묻지 않아야 함           |
| “30% 증가”만 있음 ↔ 비교 기간·대상 추가      | 부분 근거와 충분한 근거 구분                     |
| 낯선 표현·맥락 생략                          | 근거 부족과 모델 불확실성을 구분                 |

친구의 이력서 처리 동의를 학습·평가셋 저장 동의로 확대하지 않는다. 이번 진단에는 실제 개인정보·사용자 원문을 사용하지 않았다.

## 7. 파인튜닝·보정 순서

현재 12-step head 학습은 저장·재로딩 경로의 smoke 검증이다. 해당 tiny synthetic validation은 4/6으로 전후 동일했다. 본학습이나 품질 개선 증거로 사용하지 않는다.

입력·라벨 체계를 고정한 다음 동일 데이터에서 기본 모델, head-only, encoder+head를 비교한다. 현재 head-only 설정을 곧바로 정답으로 가정하지 않는다. upstream [Laya 학습 가이드](https://nandhakishorm.github.io/laya/finetune/)의 encoder/head 학습과 RLCD는 후속 비교 후보다. 먼저 단순 지도학습 기준선을 만들고, teacher 분포의 품질·비용이 확인될 때 RLCD를 비교한다. 모델이 문장으로 말하는 “90% 확신”을 교정된 soft label로 사용하지 않는다.

16GiB Mac mini에서는 작은 batch로 실제 메모리·step 시간·체크포인트 재로딩부터 측정한다. M2 Ultra나 CUDA 사례의 시간·batch를 그대로 약속하지 않는다. 지금 학습 가능성 점검이 끝났다는 이유로 전체 fine-tune의 메모리 적합성이 확인된 것은 아니다.

온도 보정은 모델과 입력 형식이 고정된 뒤, 학습/dev와 별도인 calibration 데이터에서 한다. class argmax를 고치는 작업이 아니라 확률 해석을 개선하는 작업이다. 분류별 reliability/Brier와 위험-판단 범위 곡선을 본다. 모두 보류하면 오판은 줄어도 제품은 작동하지 않으므로 precision과 coverage/recall을 함께 본다. [확률 보정 연구](https://proceedings.mlr.press/v70/guo17a.html), [선택적 분류 연구](https://proceedings.mlr.press/v130/gangrade21a.html).

추론 가속·INT8·더 작은 가중치 선택은 품질 기준 통과 후 같은 회귀셋에서 비교한다. 품질 문제를 풀기 전에 속도 최적화부터 하지 않는다.

## 8. 무엇을 만족으로 볼지

다음 숫자는 **논문에서 가져온 보장치가 아닌 첫 제품 목표 제안**이다. 사람 검수셋으로 분모와 오차를 함께 보고 조정한다. 같은 경험에서 나온 여러 prefix는 독립 표본으로 세지 말고, 경험/문서 묶음을 고려해 불확실성을 보고한다.

| 축                    | 첫 목표 제안                                               | 같이 볼 항목                                     |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 구조적 인용·시간 경계 | 회귀셋에서 없는 ID/미래 근거 사용 0건                      | 입력 누락·토큰 잘림·후보 포함률                  |
| 질문 해소             | 해소 precision ≥95%와 정답 해소 탐지 recall ≥70% 동시 충족 | 실제 해소 분모, held 비율, 같은/다른 경험별 오류 |
| 불필요한 질문         | 검수된 메모 중 이미 설명된 내용을 다시 묻는 비율 ≤10%      | 꼭 필요한 질문 탐지율, 중복률                    |
| 공고 기준             | 검수셋에서 없는 필수 조건 생성·필수/우대 뒤집기 0건        | 요건 누락률, 예외·부정별 결과                    |
| 리포트 근거           | 검수셋에서 주체·시제·수치 범위의 중대한 과장 0건           | 문장별 근거 지지율, 미기재→능력 부족 오판        |
| 실제 유용성           | 이전 버전과 블라인드 비교에서 구체성·수정 가능성 개선      | 반복 안내 비율, 사용자 수용/거부 이유            |
| 운영                  | 단계별 p50/p95·실패/복구·Codex 호출 수 측정                | 지연이 늘어난 만큼 품질이 개선됐는지             |

20개만 맞히고 모두 해소를 보류하는 모델은 통과하지 못한다. 평균값이 좋아도 팀/개인·부정·다른 경험 연결 같은 중요한 범주가 무너지면 범위를 축소한다. 작은 표본에서 오류 0건은 현실의 오류율 0%를 뜻하지 않는다. 첫 사람 검수셋으로 순위를 비교하고, 실제 지인 시험 전 별도 문서 단위 평가를 추가한다.

## 재현

backend checkout에서 실행한다. 예시 output 경로가 이미 있으면 다른 이름을 사용한다. 기존 기록을 덮어쓰지 않는다. Codex probe는 기존 로그인 CLI로 합성 텍스트를 전송하므로 실제 원문을 대신 넣지 않는다.

  --model .local/readme-laya/model \
  --data test/fixtures/readme/quality-diagnostic.json \

pnpm exec tsx src/services/readme-lab/tools/codex-quality-probe.ts \
