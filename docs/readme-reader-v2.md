# 공고 기준과 누적 독해 상태 · v2 구현 범위

2026-10-04 KST. Claude API-03 decision `37605b`가 상태·이벤트·label/facet 계약을 승인했다. 공고 기준, 원문 장부, 버전별 이벤트/브라우저 어댑터, 최종 원문 점검이 로컬 구현됐다. **모델 품질 승인을 뜻하지 않는다.** 기본 Laya는 검증된 verifier가 없어 held까지만 표시한다. partial/resolved/reopened는 검증기를 주입한 테스트 및 수동 합성 fixture에서 확인했다. 실제 계약은 [readme-lab.md](readme-lab.md)와 `contracts.ts`, 측정 결과는 [구현 증거](readme-quality-implementation-2026-10-04.md)다.

## 유지할 제품 흐름

공고 원문 → Codex CLI가 출처 있는 독해 기준 구성 → 사용자 입력 확인 → Laya가 문장을 순서대로 읽으며 질문·근거·해소 여부 분류 → 서버가 누적 상태를 갱신 → Codex CLI가 기록과 인용으로 리포트 생성.

`resolved`는 **문서 안에서 해당 질문에 필요한 설명을 찾았다**는 뜻이다. 경험이 사실임을 인증하거나 지원자의 역량을 확정하는 뜻이 아니다. 질문이 생겼다가 뒤 문장으로 해소되는 화면 요구사항은 유지한다. 현재 기본 모델의 `answers` 선택을 그대로 해소로 승격하는 것은 구현하지 않는다.

## 1. 공고에서 독해 기준 만들기

Codex CLI의 prepare 단계가 `ReaderProfile`을 만든다. 이 단계에는 이력서 내용을 넣지 않는다. 지원자를 본 후 채용 기준을 바꾸는 일을 막는다.

| 내부 필드                          | 의미·검증                                                               |
| ---------------------------------- | ----------------------------------------------------------------------- |
| `id`, `version`                    | 확인한 공고·기준 버전에 고정                                            |
| `criteria[].id`, `requirement_id`  | 원문에서 검증한 Requirement 참조. 공고에 없는 채용 요건 생성 금지       |
| `criteria[].checks[].facet`        | role / method / result / basis 중 이 요건을 설명할 때 필요한 확인 항목  |
| `criteria[].checks[].trigger`      | 언제 질문할지. 예: 관련 경험의 성과는 주장하지만 담당 역할이 없음       |
| `criteria[].checks[].sufficient`   | 어떤 설명이면 질문이 충족되는지. 예: 안내문을 직접 작성한 범위와 행동   |
| `criteria[].checks[].insufficient` | 팀 성과만 있음, 앞으로 할 계획, 다른 프로젝트, 단순 키워드 반복 등 반례 |

명시된 채용 요건과 그 요건을 읽기 위한 확인 질문을 구분한다. 공고에 수치 실적을 요구하지 않았다면 모든 문장에 숫자를 요구하지 않는다. “만족도가 높아졌다” 같은 비교 주장에만 적절한 비교 근거 질문을 적용한다. 이는 채용 요건을 추가하는 것이 아니다. 숫자를 말하지 않아도 충분한 설명일 수 있다.

요건이 없는 공고는 일반 서술 점검으로 명시한다. 직무 적합성 결론이나 임의 기준을 채우지 않는다. 기획상 일반 점검 질문의 별도 근거 유형은 계약 확정 시 함께 정한다.

## 2. 현재 문장과 이미 읽은 내용만으로 판단

서버 `ReaderMemory`는 현재 위치, 동일 경험에서 발견한 설명과 인용, 질문별 상태, 판단 이력을 보관한다. 모델의 자유 서술 요약을 사실 장부에 저장하지 않는다. 모든 설명에는 원문 unit/span과 판단 출처를 붙인다.

각 Laya 입력은 다음으로 제한한다.

- 선택한 공고 기준과 허용된 facet.
- 현재 문장, 이미 읽은 인접 문장.
- 동일 경험의 과거 근거, 아직 풀리지 않은 질문, 필요한 기존 해소 근거.
- 현재 입력이 축약됐는지 나타내는 `context_limited`.

질문 비교는 현재 문장의 일반 구체성 판정과 독립적으로 수행한다. 짧은 수치·부정·정정 문장도 이전 질문의 답이나 충돌일 수 있다. 기준/질문 선택은 이미 읽은 자료로만 하며, 전체 문서 요약·임베딩을 미리 사용하지 않는다. 동일 scope의 모든 기존 질문(최대 8기준 × 4facet)을 매 문장과 비교한다. 일부 질문을 순환 검사하면 한 번만 나온 답을 영구히 놓치므로 생략하지 않는다. 문장 상태 판정은 같은 scope의 과거 전체를 먼저 제공하고, 실제 SDK 토큰 한도 거부 때만 과거 설명 후보와 최근 문장으로 축약한다. 축약 상태에서는 새 누락 질문을 만들지 않는다. 관계 입력도 한도를 넘으면 해당 판단을 보류한다.

제목·문단 scope는 경험을 구분하는 보수적인 초기 경계다. 같은 제목 아래 여러 경험이 섞였다는 이유만으로 동일 경험을 확정하지 않는다. 명시된 이름/기간 등 근거로 같은 경험을 확인하지 못하면 연결을 보류한다. 미래 문장에서 얻은 경험 분류를 과거 판단에 소급하지 않는다.

## 3. 선택형 판단과 상태 전이

현재 구현된 Laya head는 다음을 선택한다. 이는 라벨/입력 구조를 추가한 것이며 이 과제용 가중치 학습을 마쳤다는 뜻이 아니다.

- `reader_unit`: 수행 주체 self/team/other/unknown, 수행 상태 performed/planned/negated/context/unknown, role/method/result/basis 각각 present/missing/irrelevant/unknown.
- `relevance`: 공고 요건마다 supports/mentions/unrelated. 단어 일치만으로 evidence 메모를 만들지 않는다.
- `reader_check`: 공고에서 작성한 질문 조건이 현재 설명에 적용되는지 needed/explained/irrelevant/unknown.
- `reader_relation`: 기존 질문과 현재 문장의 경험 범위 same/different/unknown, 설명 관계 complete/partial/conflict/unrelated/unknown.

점수 0.75 미만은 unknown으로 취급한다. 이는 확률 보정이나 품질 승인을 거친 임계값이 아니다. span 선택 head는 아직 없다. 메모 위치는 서버가 현재 unit의 검증된 범위로 만들고, 최종 리포트는 원문과 정확히 일치하는 인용을 UTF-16 범위로 변환한다.

서버는 인용 범위, 기준 참조, 같은 경험 여부, 질문의 충족 조건, 입력 누락, 중복 여부를 검증한 뒤 상태를 바꾼다. 질문 식별자는 `scope_id + criterion_id + facet`으로 만든다. 동일한 질문을 매 문장 다시 생성하지 않는다.

| 조건                                  | 상태·표시                                                |
| ------------------------------------- | -------------------------------------------------------- |
| 필요한 설명이 아직 없음               | open + 최초 질문 메모                                    |
| 일부 설명만 발견                      | partial + 발견한 설명/남은 질문 연결                     |
| 충족 조건을 만족하는 근거 발견        | resolved + 근거 연결. 원래 질문은 보존                   |
| 해소 근거와 충돌하는 후속 설명        | reopened + 새 충돌 근거. 이전 해소 기록도 보존           |
| 입력·모델 불확실성으로 결정할 수 없음 | 상태를 임의로 해소하지 않음. 필요한 경우 held, 사유 기록 |
| 새로 의미 있는 변화 없음              | 메모 추가 없음. 읽기 진행만 갱신                         |

이 표의 partial/resolved/reopened는 검증기를 주입한 상태 전이 테스트와 합성 시안에서 확인한 동작이다. 실제 기본 모델 실행은 후보를 held까지만 표시한다. 모델 보류와 문서의 설명 부족은 서로 다른 사유다. 전자를 후자로 바꾸어 지원자에게 보완을 요구하지 않는다. 종료 시 open은 open_at_end 이벤트로 확정한다. reopened, partial, held는 그대로 보존하고, 리포트 모델이 뒤에서 상태를 바꾸지 않는다.

## 4. 화면에 전달할 변경 제안

기존 unit/span/seq/폴링/문서 복귀 계약은 유지한다. 다음 확장을 승인된 범위에서 구현했다.

1. `Question`에 `criterion_id`, `facet`, `evidence_unit_ids`, `state_version` 추가. status에 `partial`, `resolved`, `reopened` 추가.
2. `Note.kind`에 `resolves` 추가. 기존 question/hold/evidence/observation 보존.
3. `question_updated` 이벤트: `{question_id, previous_status, status, evidence_unit_ids, state_version, at_unit_id, question}`. 생성 때 previous_status=null, question은 label/facet 등을 포함한 불변 전체 snapshot이다. 새 seq를 부여하고, 같은 이벤트 재수신은 기존 커서 규칙으로 중복 제거한다. `ReadingState.questions`가 최신 상태를 노출한다.
4. `generation.policy_version`으로 v2 식별. v1의 held를 UI에서 자동으로 resolved로 읽지 않는다.
5. 리포트의 questions는 누적 장부에서 확정. 요약 모델이 상태를 새로 판정하지 않음.

메모 문장은 기준·질문 facet·실제 인용·상태 변화로 구성한다. 예: “일정 조정 경험을 보는데, 이 문장에는 팀 활동만 나와 본인 역할이 궁금합니다.” → “뒤 문장에서 일정표 작성과 안내를 직접 맡았다고 설명했습니다.” 고정 보류 문장을 줄이는 것만으로 이 품질이 구현됐다고 간주하지 않는다.

## 5. 구현·평가 순서

1. 공고 기준 컴파일과 출처 검증, 누적 상태 전이/이벤트 계약을 구현한다.
2. 사람이 검토한 prefix 사례를 먼저 고정한다. 역할이 먼저 나온 경우, 팀/개인, 실제/계획, 부분/완전 답변, 같은/다른 경험, 나중의 정정, 메모 없는 문장, 모든 판단 보류를 포함한다.
3. 현재 모델과 새 로직을 같은 사례로 비교한다. 불필요한 질문·중복 질문·잘못된 해소·뒤 문장 답변 탐지·보류 비율·인용 정확도를 별도로 기록한다. 보류를 줄인 것만으로 정확도가 높아졌다고 보고하지 않는다.
4. 실패 유형에 맞춰 학습 데이터를 만든다. Codex 초안 라벨은 정답이 아니다. 전체 문서를 본 정답을 과거 prefix에 붙이지 않는다. 경험/시나리오 그룹 단위로 학습·검증·보정·평가를 분리한다.
5. 본학습 후 독립 평가와 보정을 거쳐 서비스 적용 여부를 결정한다. 현재 12-step smoke나 미보정 0.65 임계값은 승격 근거가 아니다.

## Claude 리뷰별 처리 범위

- H1: v1의 반복 억제에 이어 v2 기준·누적 기억을 구현했다. 기본 모델의 새 head 판단은 과도한 보류가 관찰돼 실제 메모 품질은 미달이며 본학습/검수 과제로 남는다.
- H2: 8블록·40문장, 메모 11개/질문 5개, 서로 다른 리포트 문구의 수동 합성 v1 fixture와 별도의 v2-transitions fixture를 제공했다. v2는 질문→partial→resolved→reopened 및 원문 연결을 보여준다. 모두 실제 모델 출력·정확도 증거가 아니다.
- H3: 질문 해소라는 제품 요구와 전이를 구현했다. 기본 모델의 높은 점수만으로 해소하지 않는다. 실제 실행 중 Codex 검증기 추가 제안은 decision `8e5f7c`에 별도로 남겼으며 현재 오프라인 비교에만 사용한다.
- M1/M2: HTML 오류 정규화, 읽기 폴링 한정 최대 3회 재시도, 선택적 연결 상태 콜백. 요청당 10초 제한, 대기 1/2/4초. 원문/메모/커서는 유지하고 서버 job을 실패로 바꾸지 않는다.
- M3: 비내용 사용 이벤트와 의견 저장은 미구현이다. R10의 이벤트명/허용 속성을 별도 경로 소유권에 맞게 정하고, 자유 의견의 저장 위치·보관 기간·인용 동의를 확정한 뒤 연결한다. 기존 입력 동의를 의견 공개 동의로 재사용하지 않는다.
- L1: 서비스와 실제 smoke가 같은 `README_CODEX_BIN`/`README_CODEX_MODEL` 설정을 사용하도록 맞췄다. 기본 실행 파일은 절대 경로 `/opt/homebrew/bin/codex`다. 로그인 확인도 동일한 파일로 한다.
