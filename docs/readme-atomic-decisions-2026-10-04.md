# 질문 분해 비교 · Laya / Jev

2026-10-04. 사용자가 기존 Codex 전체 독해의 40문장·약 15분 지연을 문제로 지적해, 판단 질문을 작게 나누고 같은 자료로 Laya와 Jev를 비교하는 오프라인 경로를 추가했다. **실제 HTTP 독해 엔진·화면·가중치·리포트 정책은 바꾸지 않는다.**

## 비교에서 고정하는 것

- 같은 체크포인트, 같은 한국어 원문 prefix, 같은 질문 대상과 충족 조건을 사용한다.
- 기존 설계는 `runtime.READER_RELATION` 그대로다. 새 설계는 경험 연결·질문 관련성·기존 답의 정정 여부를 각각 묻고, 역할에는 개인 담당/수행/구체적 업무, 수치 근거에는 전/후 값·측정법·조건 비교 가능성을 추가한다.
- 질문 결과를 코드에서 합친다. 경험이 다르면 연결하지 않고, 질문과 무관한 정정으로 기존 답을 철회하지 않는다. 충분한 사실을 모두 확인한 경우에만 `complete`다. 높은 확신의 설명 누락/명시적 부정은 구분해서 `partial`에 기록한다. 낮은 확신을 설명 누락으로 바꾸지 않는다.
- 모델 입력은 `question`, `sufficient`, `insufficient`, `original`, `current`, `evidence`만 포함한다. 정답·사례 ID·미래 문장·기대 사실은 입력에 넣지 않는다. 두 미래 문장 사례는 현재 위치 뒤 텍스트가 입력에 없음을 검사한다.
- 질문 정의와 39개 합성 사례, 실행 순서, 소스 해시를 호출 전에 저장한다. 기존/새 설계와 정순/역순을 seed 24로 섞어 실행한다. 시범 호출 1회와 모델 로딩은 별도 기록한다.

## 측정과 한계

원시 판단 일치, 0.75 gate 후 일치, 채택 수와 채택 오류, 잘못된 해소·정정, 해소 누락, 선택지 순서에 따른 판단·채택 변화, 질문 수와 호출 시간을 함께 기록한다. 0.75는 기존 진단 기준을 고정한 것이며 정확도 75%나 새 과제의 확률 보정을 뜻하지 않는다. Laya `answer_confidence`와 Jev `confidence`도 같은 정의라고 가정하지 않는다.

모든 라벨은 `provisional_agent_authored`, `human_reviewed=false`다. 기대 사실을 넣었을 때 코드 결합표가 기대 관계와 일치하는 검사는 코드 검증이며, 사람 정답이나 모델 성능 검증이 아니다. 사람 역할과 수치 개선 근거 두 유형에 한정한다. 모든 직무의 요건·부정으로 충분히 답할 수 있는 사실 질문·독립 근거 메모의 정정 등을 포괄하지 않는다.

이 실험은 이미 정해진 질문과 공통 과거 원문을 제공한다. 모델이 자기 판단을 누적하는 전체 독해, 새 질문 생성, 원문 인용 생성, 리포트 유용성은 시험하지 않는다. **정답률만으로 운영 채택하지 않는다.**

80·160회 부하 시험은 같은 합성 prefix 사례들을 순서대로 재사용하는 처리량 시험이다. 80·160문장짜리 실제 이력서의 독해가 아니다. 긴 문맥, 누적 질문 수, 공고 준비, 문서 파싱, 최종 리포트, 대기열·동시 사용자가 빠져 있으므로 기존 약 15분과 직접 비교하지 않는다. 각 부하의 실제 호출 수·질문 수·총 시간·p95를 저장한다.

## Jev 실행 설정

공식 HTTPS API만 사용하고 버전은 `jev-1.13.0`으로 고정한다. 키는 `TYPESAFE_API_KEY` 환경변수로만 읽는다. `--provider jev`와 `--allow-remote`가 모두 있어야 호출한다. 원문·키가 포함될 수 있는 외부 오류 본문이나 헤더는 저장하지 않고, 모델/답/확률/사용 토큰/시간만 허용 목록으로 기록한다. 리다이렉트는 거절하고 타임아웃은 30초, 자동 재시도와 다른 모델로의 대체는 없다. 응답의 모델 버전·확률 분포·토큰 계수가 잘못되면 실패로 기록한다.

macOS zsh 터미널에서 키를 화면이나 명령 기록에 남기지 않고 입력한 뒤 **같은 터미널에서** 실행한다. 키를 채팅이나 저장소 파일에 붙이지 않는다.

```sh
read -rs 'TYPESAFE_API_KEY?Jev API key: '
export TYPESAFE_API_KEY
python3 src/services/readme-lab/python/decision_eval.py \
  --provider jev --allow-remote \
  --data test/fixtures/readme/atomic-decisions-v1.json \
  --out .local/readme-laya/atomic-jev-new
unset TYPESAFE_API_KEY
```

Jev 기본 시험은 모델 로딩 없이 워밍업 1회와 비교 156회로 구성한다. API 실패 시 후속 호출을 중단한다. 원문은 합성 자료로만 제한한다. 공식 공시 가격은 2026-10-04 확인 기준 입력 100만 토큰당 $0.042, 출력 무료다. 비교 실행의 `run.json`에는 실제 응답의 입력 토큰으로 계산한 **비교 호출 부분만의 추정 요금**을 저장하며 워밍업·선택 부하·다른 서비스 비용은 이 숫자에 포함하지 않는다. 이는 청구서 확인이 아니다.

참고: [공식 API](https://docs.typesafe.ai/api), [모델·가격·언어 지원](https://docs.typesafe.ai/models), [확신도 정의](https://docs.typesafe.ai/confidence), [질문 분해 권고](https://docs.typesafe.ai/introduction), [알려진 약점](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

이번 표본에서는 Jev와 질문 분해 조합이 가장 유망하다. 그러나 정순 원자 설계는 39개 중 **22개를 보류**했고, 설명 보충이 필요하다고 정의한 `partial` 17개 중 최종 `partial`은 1개뿐이었다. 실제 수치 철회 사례도 하나 보류됐다. 따라서 원시 일치 34/39를 사용자 정확도나 충분한 피드백 제공률로 표현하지 않는다. 보류를 피드백할 내용이 없다는 뜻으로 처리하면 유용한 보충 요청을 놓친다.

- `basis-ambiguous-scope`: 검색 API 개선 주장 뒤에 “어느 API인지는 밝히지 않았지만” 전후 측정값을 적었다. 동일 경험인지 확정하지 않는 `unknown`이 기대값인데, 원자 설계는 두 순서 모두 경험 연결 확신도 0.93으로 `complete`를 채택했다. 문장 인접성을 연결 근거로 읽을 여지는 있으므로 사람에게 라벨 정책을 확인해야 한다. 높은 확신도만으로 이 연결을 검증할 수 없다.
- `role-scope-unknown`: 전시 운영 뒤에 시점·장소를 밝히지 않은 안내문 작성 경험을 적었다. 원자 정순은 보류했지만 역순은 연결 확신도 0.75로 해소를 채택했다.
- `role-other`: 전시를 도왔다고만 한 사람이 안내문 작성은 동료가 했다고 보충했다. 앞에서 자신이 작성했다고 주장한 적이 없는데 기존 설계는 두 순서 모두 정정으로 채택했다. 원자 설계도 원시 정정 판단은 남아 있고 gate 후 보류했다.

정순↔역순의 최종 원시 관계 차이는 기존·원자 각각 1/39, gate 후 차이는 기존 7/39·원자 2/39였다. 원자 개별 질문 답은 12/251개 달랐다. 같은 순서 반복 대조군을 두지 않았으므로 이 차이를 선택지 순서만의 인과 효과로 단정하지 않는다.

서버 왕복을 포함한 관찰값이며 재시도는 없었다. 현재 Laya 원자 설계 중앙값 298ms보다 빨랐지만, Laya 기존 설계 87ms보다는 느렸다. 주된 이득은 기존 Codex 전체 독해 대신 좁은 판단을 빠르게 처리할 수 있다는 가능성이다. 공고 기준·질문 생성·누적 독해·최종 리포트는 이 비교에 포함되지 않았다.

### 같은 긴 입력으로 추가 확인

`decision_context_probe.py`에 명시적인 Jev 옵션을 추가했다. Laya 긴 입력 시험과 `inputs.json`이 바이트 단위로 같고, 질문·상태 구성도 그대로다. 역할/측정 2개 사례 × 2·40·80·160구간 × 기존/원자 = 16건을 호출했다. 로컬 기본 provider는 Laya로 유지한다.

- 16건 모두 응답했고 원시 관계는 모두 기대한 `complete`였다. 요청 시간은 196–274ms였다.
- 기존 설계 8건은 모두 gate 후에도 해소했다. 원자 설계는 짧은 대조군 2건만 해소하고, **40·80·160구간 6건 모두 낮은 확신의 질문 때문에 보류**했다.
- 160구간의 원문은 7,206/7,237자였다. 이 배경을 넣은 한 번의 요청은 약 224–250ms였다. 160구간 전체를 순차적으로 읽고 리포트를 만드는 시간은 아니다.
- 클라이언트는 입력을 자르지 않고 보냈다. Jev 내부 토큰화·문맥 절단은 API에서 관찰할 수 없어 `state_stats`와 `token_guard_rejected`를 `null`로 기록했다. 응답 성공만으로 내부 절단이 없다고 보장하지 않는다.
- 실제 이력서의 여러 경험·방해 정보·대명사·정정을 재현한 자료가 아니라 반복 배경을 넣은 길이 탐색이다. 긴 입력의 품질 검증이나 실서비스 처리시간 검증은 아니다.

같은 터미널에 키가 설정된 상태에서 새 경로로 재현할 수 있다.

```sh
python3 src/services/readme-lab/python/decision_context_probe.py \
  --provider jev --allow-remote \
  --data test/fixtures/readme/atomic-decisions-v1.json \
  --out .local/readme-laya/atomic-jev-context-new
```

### 다음 구현 판단

Jev를 빠른 판별기의 우선 후보로 두고, Codex는 공고 기준·질문 설계와 최종 리포트에 사용하는 구성이 합리적이다. 다만 이번에 서비스 엔진을 교체하지는 않았다. 우선 같은 경험의 근거인지 명시적으로 연결하고, 누락과 불확실성을 구분하며, 보류된 중요한 질문만 추가 판별하는 흐름이 필요하다. 매 문장마다 Codex를 호출하면 기존 지연을 되풀이할 수 있다.

0.75를 일괄적으로 낮춰 이 39개에 맞추지 않는다. 보충 요청이 필요한 사례의 채택률, 근거 연결 오류, 철회 탐지, 별도의 미사용 자료와 사람 검수를 함께 봐야 한다. 다음 품질 평가는 여러 경험을 포함한 40줄 이상 합성 문서의 질문 생성부터 최종 리포트까지 실제 시간·호출 수·사용 토큰·근거 누락을 측정해야 한다. 현재 시험으로 전체 파이프라인의 목표 속도나 피드백 유용성을 달성했다고 볼 수 없다.
