# Codex 순차 독해 기준선 · 검증 기록

사용자가 지정한 우선순위는 **판단 정확성과 피드백 유용성**이다. 이 작업의 합격 기준은 [품질 목표](readme-quality-target.md)에 먼저 고정했다. 아래 숫자는 합성 시나리오의 동작 검사이며 사람 정답셋 정확도가 아니다.

위 최신 시험군의 독립 검토에서 중요한 판단 오류를 관찰하지 않았다. 실제 지인 문서의 유용성·사람 정답셋 정확도·운영 품질은 미검증이다. Laya 실험 가중치는 품질 기준에 미달해 승격하지 않았다. Codex HTTP 연결은 미적용 패치로 검증했으며 공유 엔진 계약 `00986b`의 확인과 실제 화면 활성화는 남아 있다.

완료 감사에서 목표 4번을 독해 단계에만 한정하면 최신 전체 흐름의 일반화 점검을 완전히 입증할 수 없다고 판단했다. 이를 보완하기 위해 `semantic-final-pipeline-v5.json`에 새로운 표현·업종의 8사례를 추가했다. 이전과 같은 행동 계열의 첫 사용 표현이며, 새로운 추론 유형 8개라고 주장하지 않는다. 모든 사례는 실제 공고 기준 생성과 리포트까지 실행한다. 사전 독립 검토에서 사진 준비 행동의 철회 범위가 모호한 한 문장을 **첫 호출 전에** 명확히 했고, 기대 동작·소스·데이터를 고정했다. 현재 실행의 데이터 해시는 `2b6954bcbe44465613ca0f0e6f34aac05e81bd65560d6095a9672dc20e321e33`, 동결 기록은 `.local/readme-laya/semantic-final-pipeline-v5-freeze.json`이다. 실행 `semantic-final-pipeline-v5-run1`과 독립 내용 검토가 모두 완료되어 목표 4번·5번의 최신 전체 흐름 확인을 충족했다.

## 구현한 변화

`semantic-reader.ts`는 현재 문장까지의 원문, 공고에서 만든 기준, 이전 질문/메모만 Codex CLI에 보낸다. 필요한 질문, 실제 행동의 근거, 기존 질문의 부분 설명·해소·정정만 반환하도록 하고 중요한 메모를 별도 호출로 검토한다. 원문 인용과 참조를 결정적으로 검사한 후 상태를 한 번에 반영한다. 질문 원문과 이전 필기는 유지하고 후속 문장에서 새 상태를 추가한다.

문단 경계와 경험 경계는 다르게 취급한다. 한 문단의 별개 프로젝트는 별도 질문을 가질 수 있고, 명시적으로 같은 경험인 다른 문단은 연결할 수 있다. 이미 답한 내용, 미래 계획, 타인의 일, 무관한 배경에 불필요한 질문이나 긍정 근거를 만들지 않도록 검사한다. 소수점·날짜·Node.js 같은 표기가 문장 중간에서 끊어지지 않도록 추출 단위를 보강했다.

`semantic-pipeline.ts`는 실제 순서대로 독해 이벤트를 내보내고 최종 리포트까지 실행한다. 중간 실패는 완료로 바꾸지 않으며 이미 완료한 단계와 원래 필기를 보존한다. 취소와 전체 실행 제한을 구분한다. 독해 호출은 45초, 공고 분석·리포트 호출은 120초 제한이다. 시간 초과에 한해서 같은 입력으로 새 프로세스에서 한 번만 재시도한다. 잘못된 출력이나 사용자 취소를 프로세스 재시도로 숨기지 않는다. 구조·의미 검토에 거절된 초안은 한 번만 재작성하며, 거절된 초안과 구체적인 오류를 함께 전달한다. 전체 독해+리포트 제한은 15분이다. 40단위 독해에 551초가 걸려 기존 10분 제한이 리포트 호출을 중단한 실제 결과에 따라 늘렸다. 단계별 검증과 호출 제한은 유지했다.

리포트의 인용과 메모 연결도 검사한다. 각 메모는 같은 항목에 인용한 원문 중 하나에 실제로 연결되어야 한다. 연결 오류는 항목 번호·메모 ID·필요한 원문 ID를 반환하여 수정 대상을 명확히 한다. 근거 없는 연결을 허용하거나 검증을 제거하지 않았다. 거절 초안 보존은 합성 평가 도구의 명시적인 진단 훅에만 있으며 정상 서비스는 해당 훅을 사용하지 않는다.

`ReaderMemory.engine`으로 실제 독해 엔진을 명시한다. 순수 Codex 결과에 Laya 안내가 붙던 공통 문구를 수정했고, 추출된 원문 전체의 순차 독해와 리포트가 클라우드에서 처리된다는 범위를 명시한다. Mac mini는 로그인된 CLI와 순서를 관리하며 Codex 모델 자체가 로컬에서 실행되는 것은 아니다. API 키를 추가하지 않았다.

## 긴 문서에서 발견한 추가 오류

추가 40단위/8문단/1,510자 합성 자기소개서의 첫 실행(`semantic-long-flow-run1`)은 9단위 뒤 10번째 단계에서 의미 검토에 두 번 거절되어 중단됐다. 완료된 기록에서도 한 오류를 발견했다. 안내문 역할 질문이 해소된 뒤 “행사 일정 항목을 직접 작성했다”는 추가 설명을 앞선 답의 철회로 잘못 처리했다. 독립 검토도 false reopen으로 확인했다. 32개 짧은 시험에서 중요한 오류를 관찰하지 않았다는 결과를 모든 문서에 대한 보장으로 확대할 수 없음을 보여준다.

이 상태 오류와 다음 단계 중단은 각각 확인된 사실이다. 당시 reader 초안·감사 결과는 보존하지 않았으므로 앞 오류가 다음 실패를 유발했다는 인과관계는 확인되지 않았다. 이후 합성 평가 진단 훅을 reader까지 확장했고 단계/문장/시도마다 다른 파일로 저장한다. 서비스의 원문 기록 정책은 바꾸지 않았다.

개선 규칙은 “원래 질문의 충분성이 유지되는 구체화는 해소를 유지하고, 실제 원문이 이전 답을 부정하여 원래 질문이 다시 미설명이 되는 경우만 재확인”이다. 이전 모델 메모의 표현을 원문 사실로 취급하지 않는다. conflict는 뒤집힌 이전 답의 원문을 하나 이상 함께 인용해야 한다. 이는 의미 검토를 보완하는 조건이며 인용 존재만으로 모순을 승인하지 않는다.

회귀 데이터 `semantic-clarification-v1.json`은 신규 구체화/철회 반례 3개와 이미 관측한 확인 사례 8개다. 새 독립 평가군으로 부르지 않는다. 40단위 원문도 첫 실패 이후에는 개발 재검증군이다. 원문의 “매장 문의의 25% 감소”라는 표현은 뒤의 분 단위 비교로 처리시간을 뜻하지만 문구 자체는 모호하다는 검토 의견을 보존한다. 실행 중 데이터를 수정하지 않았다.

수정 후 실제 회귀 실행 `semantic-clarification-run1`은 11/11 동작 검사와 독립 내용 검토를 통과했다. 29단계 p95 21,443ms, 해소 상태 확인 12/12(새 해소 10회, 해소 유지 2회), 메모 22개다. 두 구체화는 해소 유지·중복 없음, 실제 작성자 부정은 재확인, 이후의 실제 교정 업무는 재해소했다. 이 실행에서 중요한 의미 오류를 관찰하지 않았다. 저장 소스 10개와 데이터 해시도 독립 검토했다. 40단위 재실행과 추가 미사용 8사례 확인 결과는 완료 후 기록한다.

40단위 2차 실행(`semantic-long-flow-run2`)은 독해를 551,183ms에 마쳤으나 리포트가 48,840ms 뒤 전체 10분 제한으로 취소됐다. 독립 검토에서 구체화의 해소 유지와 실제 작성자 정정의 재확인은 맞았지만, 또 다른 P2를 찾았다. 동료의 측정, 3월 12분→5월 9분, 동일 매장 전체 문의가 설명된 뒤에도 별도 확인 자료를 요구하여 수치 질문을 partial로 남겼다. 생성된 공고 독해 기준이 문서 설명 점검을 실제 성과 입증 의무로 확대한 문제다. 이 실행은 독해 품질 전체 PASS가 아니며 리포트 검토 결과도 없다.

이후 공고 기준 생성/감사, 독해/감사, 기존 전이 검토, 리포트/감사에 공통 서술 충족 원칙을 적용했다. 비교 지표·전후 값·대상·기간의 설명은 문서 기준으로 판단하고 공고에 없는 별도 첨부/증빙을 필수화하지 않는다. 공고의 명시 제출 요건은 보존한다. 단순 개수 서술에는 전후 비교를 강요하지 않는다. `semantic-explanation-flow.json`과 `semantic-required-material-flow.json`은 이 두 경계를 분리한 합성 개발 반례다. 평가 실행 결과는 별도로 확인한다.

원래 24사례의 2차 실행은 이 증빙 경계 수정 전에 시작했다. `correction_reopens`가 의미 검토에 두 번 거절된 실패를 보존한다. 당시 사례별 거절 진단이 없으므로 원인을 확정하지 않는다. 작성 근거를 철회하고 배포/인쇄만 했다는 설명과, 실제 작성 범위를 구체화한 설명의 차이를 생성/감사 양쪽에 명시했다. 후속 2사례 실행(`semantic-boundary-focus-run1`)은 두 동작이 통과했지만 평가 하네스의 모델 메타데이터 변수 범위 오류로 최종 집계를 저장하지 못했다. 각 사례 결과는 남아 있으며 이를 완전한 시험군 성공으로 계산하지 않는다. 독립 검토가 발견한 하네스 오류를 수정하고 typecheck를 통과했다.

서술/증빙 경계 반례의 첫 전체 실행(`semantic-explanation-flow-run1`)에서 독해는 수치 비교를 해소하고 미첨부에도 유지했지만, 리포트에서 또 두 결함이 발견됐다. 여러 문장의 사실을 서술하면서 첫 문장만 인용했고, 160자 끝에서 문장을 끝내지 못했다. 서버가 절단한 결과가 아니라 초안 자체의 결함이며 기존 전체 원문 감사가 놓쳤다. 이 실행을 리포트 PASS로 기록하지 않는다.

이후 리포트에는 두 층의 의미 검토를 적용했다. 첫 검토에는 각 항목의 observation과 그 항목의 실제 인용문만 제공한다. 다른 원문에서 누락된 링크를 대신 찾아 승인할 수 없도록 한 것이다. 두 번째 검토는 모든 원문을 사용해 이미 설명된 내용을 없다고 판단하는지와 제안의 타당성을 확인한다. 비어 있지 않은 문장 필드가 종결 문장부호로 끝나지 않으면 원문을 잘라내거나 마침표를 붙이지 않고 재작성 대상으로 돌린다. 이 기계적 조건만으로 문법·의미 완결을 보장하지 않으므로 의미 검토도 유지한다.

완료된 독해에서 리포트만 다시 실행하는 도구는 원래 실패 기록뿐 아니라 성공 기록도 명시적으로 선택할 수 있다. 원본 파일 경로·해시·최신 리포트 소스 스냅샷과 `resumed_report_only=true`를 저장한다. 재생성 시간을 최초의 연속 실행 시간으로 합치지 않는다.

`semantic-v1-run2`는 23/24로 끝났고 정정 사례가 의미 감사에 거절되어 중단됐다. 실패 기록을 보존했다. 후속 3차가 같은 24사례를 다시 통과한 결과와 별도로 본다. `semantic-long-flow-run3`는 40단위+리포트를 전체 756,511ms에 끝냈다(독해+리포트 701,590ms). 15분 제한으로 끝까지 실행할 수 있다는 근거이지만 증빙 경계 보강 전 코드라 수치 질문이 여전히 partial이므로 품질 PASS는 아니다.

현재 리포트 인용 감사는 항목마다 별도의 새 CLI 프로세스를 사용한다. 각 프로세스에는 그 항목의 observation과 인용문만 제공하며, 다른 항목의 인용도 전달하지 않는다. 동시에 두 개까지만 실행하고 실패 시에도 시작한 작업을 모두 회수한 뒤 반환한다. 전체 원문 검토는 그 다음 단계다. 자동 검사만으로 일반 문서의 정확도를 보증하지 않으며, 실제 출력의 독립 내용 검토를 계속 병행한다.

긴 문서 4차(`semantic-long-flow-run4`)는 수치 질문을 해소했으나 역할 질문이 끝까지 partial로 남는 새 오류를 드러냈다. 분류와 접수정보 입력이라는 본인 업무가 설명됐는데, 공고의 ‘처리 기록 관리’를 상태 갱신 업무로 확장하고 그 업무까지 했어야 role을 충족하도록 판단했다. 전체 701,955ms에 끝났지만 품질 PASS가 아니다. 짧은 별도 역할 범위 사례(`semantic-role-scope-flow-run1`)가 PASS인 사실을 이 긴 사례의 실패 대신 쓰지 않는다.

공통 정책에 facet 분리를 추가했다. role은 해당 경험에서 본인이 맡은 구체적 부분을 설명하면 충족한다. 복합 공고 업무 전체 수행이나 method/result/basis의 충족을 role 해소에 추가하지 않는다. 이미 작성된 질문에 여러 공고 업무명이 묶여 있어도 실제 맡은 범위로 판단한다. 이 해소는 직무 전체 자격의 인증이 아니며 타인의 업무를 본인에게 연결하지 않는다. 원래 질문 이력은 지우지 않는다.

이 보강 후 일반화 확인은 수작업 독해 기준을 주는 방식에서 더 확장했다. `semantic-generated-confirmation-v3.json`의 미사용 8사례는 공고 원문으로 실제 CLI 기준 생성부터 실행한다. 하네스의 `profile_job_text` 입력을 사용하며, 고정 checks는 이 경로에서 사용하지 않는다. 실제 준비 단계 실패는 사례 실패로 남기고 합성 기준으로 대체하지 않는다. 기존 24사례와 40단위 문서도 별도 재검증한다.

항목별 감사의 영구 오류 뒤 다른 worker가 대기 항목을 계속 시작하던 실행 결함도 독립 검토에서 발견하여 수정했다. 첫 예외 뒤 새 항목 배정을 멈추고 이미 시작한 작업만 회수한다. 모델 없이 실제 Reasoner의 프로세스 호출을 대체한 회귀 검사에서 작성 1회+이미 시작한 감사 2회만 호출되고 대기 3개는 시작하지 않음을 확인했다. 실패한 항목을 승인하거나 재시도 제한을 늘리지 않았다.

내부 `retractions` 출력과 중복 방지용 `note_retractions` 기록을 추가했다. 이전 질문 미연결 evidence만 대상으로 허용하고, 해당 필기의 실제 원문 구절과 현재 정정 문장을 모두 요구한다. 같은 문장의 무관한 절을 인용해 다른 메모를 철회하지 못하도록 필기 범위와 인용의 비공백 겹침을 검사한다. 감사 입력에는 대상 필기의 정확한 `anchor_quote`를 제공하여 실제 주장 모순인지 따로 검토한다. 이 기록은 공개 API에 추가하지 않는다.

독립 검토에서 수정 결과의 모든 항목을 삭제해 빈 리포트로 성공 처리될 수 있는 경로를 발견했다. 이제 이 경우 `report_repair_empty`로 실패하고 독해 기록을 보존한다. 같은 행동을 역할·방법으로 나누기만 한 반복도 유용성 결함으로 다뤘다. 작성 단계에서 한 항목으로 묶도록 하고, 최종 감사는 다른 항목에 완전히 포함되며 고유 사실·제안이 없는 반복만 반려한다. 인용이 같거나 내용이 부분적으로 겹친다는 이유만으로 고유한 피드백을 삭제하지 않는다. 승인 항목 보존, 대상 index 검사, 전체 삭제 거절, 중복 제거 후 전체 감사 회귀를 포함한 관련 20검사와 독립 검토가 통과했다.

`proposal-real-e2e-run6`은 부분 수정 적용 후 12문장/7항목을 준비 59,152ms, 전체 382,932ms, **독해+리포트 323,780ms**에 완료했다. 독립 검토는 사실·인용, 두 질문의 u2/u6 해소, 12개 컴파일 소스 해시, 14응답/37이벤트와 재수신을 통과시켰다. 빈 결과 방지·중복 감사 추가 전 스냅샷이므로 최신 통합 결과로 부르지 않는다. 문서 작성 항목 두 개는 겹치지만 하나에 고유한 선택 제안이 있어 완전 중복으로 판정하지 않았다.

40문장 `semantic-long-flow-run7`도 실제 리포트 10항목까지 완료해 독립 검토 PASS다. 독해+리포트 **868,957ms**, 리포트 195,955ms, 준비 포함 933,848ms로 기존 15분 독해+리포트 제한 안에 끝났다. 단계 합계 673,000ms, 단계 p95 21,524ms이며 벽시계 경계에 2ms씩 오버헤드가 있다. 역할 질문은 u11, 수치 근거는 u16에서 해소됐고, 안내문 질문은 u8에서 해소→u9 구체화에 유지→u37 실제 작성자 철회에서만 재확인으로 바뀌었다. 별개의 매장 문서 작성은 u22 해소를 유지했다. 8개 저장 소스 해시·fixture, 40개 prefix 이벤트, 19개 원래 필기, 11개 질문 전이, 34인용/15메모 연결이 검토를 통과했다.

긴 실행의 첫 리포트에서 반려된 두 항목은 각각 u27/u36 인용만 추가됐고 다른 여덟 항목은 그대로 보존됐다. 여러 항목이 일부 인용을 공유하지만 각각 역할·애매한 사례 처리·공유/수정 결과의 고유 내용을 담아 완전한 의미 중복은 아니었다. 추가 리포트 재생성이 필요한 내용 결함은 발견되지 않았다. 이 실행은 **부분 수정·인용 재사용 적용 후, 빈 결과 방지·중복 감사 추가 전** 소스 `e58fc0b9`/`fd31cff9`의 개발 회귀다. 최신 정책의 근거는 별도 리포트 6사례와 API 7차이며, 버전을 섞어 전체 최신 연속 실행으로 부르지 않는다.

## 화면/API 연결 제안

현재 구현은 내부 함수·오프라인 검증 경로이다. 기존 HTTP Lab의 기본 Laya 엔진을 몰래 Codex로 바꾸지 않았다. 공유 게시판의 decision `00986b`에 다음 추가 계약을 제안했다.

- `generation.engine = "codex_cli"`
- `generation.policy_version = "readme-prefix-codex-v1"`
- `generation.model = null`; 기존 `codex_model`은 요청한 CLI 모델 표시
- 문서/인용 범위/이벤트 순번/질문 전체 스냅샷/리포트 구조는 기존 v2와 동일
- 순차 독해도 원문을 클라우드로 전송한다는 동의 문구와 실제 엔진 표시

검토 가능한 [연결 패치](proposals/codex-reader-serving.patch)를 준비했다. 실제 계약 파일에는 아직 적용하지 않았다. 원본 파일을 덮어쓰지 않고 TypeScript 컴파일러의 가상 파일 입력으로 패치를 검사·빌드했으며, 그 빌드에 Fastify 요청을 넣어 성공/중간 실패/취소와 브라우저 이벤트 재수신을 검사했다. 세 경우 모두 Laya 호출 0회, 올바른 Codex 메타데이터를 확인했다. 이는 테스트 더블 기반 연결 검사이며 실제 모델 품질 검사의 대체물이 아니다. 근거는 `.local/readme-laya/proposal-{compile,smoke}.json`이다.

[화면 연결용 예제](proposals/codex-reader-actual.json)는 실제 CLI·TXT 파서·가상 패치 HTTP 실행 `proposal-real-e2e-run7`의 응답이다. `http_wrapper_authored=false`이며 이전에 작성한 HTTP 껍데기 예제는 `.local/readme-laya/codex-reader-authored-wrapper-historical.json`, 이전 실제 HTTP 3차 예제는 `.local/readme-laya/codex-reader-actual-http-run3-historical.json`에 보존했다. 7차는 최신 리포트 정책으로 12문장·메모 8개·해소 질문 2개·리포트 5항목을 생성했다. 준비 60,176ms, 첫 메모 14,047ms, 전체 364,951ms, **독해+리포트 304,775ms**이며 한 항목의 인용 감사 거절과 수정 시간까지 포함한다. 원본 실행 SHA-256 및 12개 컴파일 소스 해시를 포함한다. 인프로세스 HTTP이고 미적용 계약의 검증용 빌드이므로 배포된 응답은 아니다. 계약 확인 전에는 활성 화면용 계약으로 취급하지 않는다.

7차의 독립 검토는 5항목의 사실·유용성, 13인용·7메모 연결, 두 질문의 올바른 해소와 14응답/39이벤트의 중복·전체 재수신을 확인했다. 반려된 첫 항목만 바뀌고 다른 네 항목은 그대로 보존됐으며, 문서 작성 역할과 방법을 반복하지 않았다. 사본의 실제 응답·시간·소스 해시도 원본과 일치한다.

패치는 `README_LAB_READER=codex_cli` 선택을 추가하고 기본값은 기존 `laya`로 유지한다. 공유 계약 확인 후 소스에 적용·검사하는 것과 운영 환경의 설정/배포는 별도다. 프런트 시각 디자인은 변경하지 않았다.

Codex 모드의 동의 문구 제안: “업로드한 문서에서 추출한 텍스트와 채용공고를 ChatGPT 로그인 Codex CLI를 통해 클라우드로 전송하여 순차 독해와 최종 피드백을 생성합니다. Mac mini는 실행을 관리하며, 모델의 판단에는 오류가 있을 수 있습니다.” 이 모드에 기존의 “Laya 문장 판단은 맥미니에서 처리” 문구를 사용하면 안 된다. 이벤트는 실제 완료 시점에 표시하고, 리포트의 인용을 누르면 원래 문장과 당시 메모를 함께 연다. 후속 해소·정정은 원래 질문과 필기를 지우지 않는 추가 상태로 표시한다.

[독립 근거 정정 예제](proposals/codex-reader-correction-actual.json)는 실제 CLI·TXT 파서·가상 HTTP `proposal-correction-e2e-run1`의 응답을 그대로 저장했다. 2문장, 2메모, 1리포트 항목, 전체 101,249ms이며 원래 evidence와 양쪽 원문에 연결된 observation을 보존한다. 독립 검토가 원본 실행 해시·준비 응답·전체 응답·시간·정정 링크의 일치를 확인했다. 부분 수정·중복 제거를 추가하기 전 리포트 코드이며 배포·새 일반화 자료는 아니다.
